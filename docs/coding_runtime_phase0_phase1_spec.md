# Coding Runtime Phase 0/1 Implementation Spec

**Document Version:** 0.1
**Date:** 2026-03-16
**Status:** Draft

## Purpose

This spec defines the first two implementation phases for extracting Sophia's coding capability into a standalone runtime service.

The target outcome is:

- `sophia_prima` remains the user-facing orchestrator
- coding execution moves behind a stable runtime contract
- backend adapters, workspace policy, artifacts, and verification become reusable runtime concerns

This spec is intentionally limited to:

- Phase 0: contract extraction inside the current `sophia_prima` process
- Phase 1: creation of an in-monorepo `sophia_forge` service and client integration

It does not attempt to fully specify later phases such as containerized execution, remote workers, or the offline eval harness.

## Scope

In scope:

- run request/result contracts
- coding runtime event model
- artifact model
- Phase 1 HTTP API
- package/module boundaries
- migration sequence from current `coding_worker` integration
- acceptance criteria and test plan

Out of scope:

- remote execution infrastructure
- branch/PR automation
- multi-tenant auth
- production deployment topology
- full Phase 2 eval platform

## Current Integration

The current control path is spread across `sophia_prima`:

- `agents/sophia_prima/src/sophia/subagents.py`
  - decides when coding work should be delegated
- `agents/sophia_prima/src/sophia/agent.py`
  - defines the `coding_worker` subagent profile and orchestrates delegated work
- `agents/sophia_prima/src/sophia/coding_workers/base.py`
  - defines the execution contract and workspace policy enforcement
- `agents/sophia_prima/src/sophia/coding_workers/codex.py`
  - runs the Codex backend
- `agents/sophia_prima/src/sophia/coding_workers/claude_code.py`
  - runs the Claude Code backend
- `agents/sophia_prima/src/sophia/events.py`
  - emits generic subagent lifecycle events
- `agents/sophia_prima/src/sophia/gateway/run_store.py`
  - persists gateway runs and artifacts

Current strengths:

- coding execution is already backend-pluggable
- filesystem policy is explicit
- outputs are structured
- run/event persistence patterns already exist elsewhere in the system

Current weaknesses:

- coding contracts are owned by `sophia_prima`
- coding lifecycle is expressed only as generic subagent activity
- artifacts are backend-centric rather than runtime-centric
- there is no service/API boundary for non-`prima` clients

## Design Goals

1. Make coding execution callable by multiple clients.
2. Preserve existing backend portability.
3. Keep the initial API and data model small.
4. Avoid a repo split until the runtime interface stabilizes.
5. Preserve local development ergonomics.
6. Keep Phase 0 backward-compatible for `sophia_prima`.

## Non-Goals

1. Replace `sophia_prima` as the primary UX.
2. Generalize the runtime into a universal workflow engine.
3. Solve sandboxing/isolation beyond the current workspace model in Phase 1.
4. Introduce broad organizational auth or billing concerns.

## Terminology

- `client`: the caller of the coding runtime, such as `sophia_prima`, CLI, or CI.
- `run`: one bounded coding task submitted to the runtime.
- `backend`: Codex, Claude Code, or another execution engine.
- `artifact`: a persisted object produced during or after the run.
- `verification`: a targeted check run by the runtime after implementation.

## Phase 0: Contract Extraction

### Objective

Extract coding-runtime contracts out of `sophia_prima` without changing behavior.

### Deliverables

Create a shared protocol package:

- `shared/sophia_forge_protocol/`
  - `run_models.py`
  - `event_models.py`
  - `artifact_models.py`
  - `verification_models.py`

Retain the backend implementations in `agents/sophia_prima` during this phase, but move all durable contracts into the shared package.

### Required Models

#### `RunRequest`

```python
class RunRequest(BaseModel):
    run_id: str | None = None
    client_name: str
    task: str
    workspace_root: str
    writable_roots: list[str]
    readable_roots: list[str]
    backend: Literal["codex", "claude_code"]
    timeout_sec: float
    verification_policy: "VerificationPolicy"
    metadata: dict[str, Any] = {}
```

Notes:

- `run_id` may be client-supplied or generated by the runtime.
- `metadata` should carry initiator context such as `session_id`, `agent_id`, or source channel.

#### `RunStatus`

```python
Literal[
    "queued",
    "running",
    "completed",
    "blocked",
    "failed",
    "timed_out",
    "cancelled",
]
```

#### `RunResult`

```python
class RunResult(BaseModel):
    run_id: str
    status: RunStatus
    summary: str
    changed_files: list[str] = []
    verification: list["VerificationResult"] = []
    follow_ups: list[str] = []
    artifact_ids: list[str] = []
    error: str | None = None
```

#### `RunArtifact`

```python
class RunArtifact(BaseModel):
    artifact_id: str
    run_id: str
    artifact_type: Literal[
        "task_spec",
        "prompt_package",
        "backend_output",
        "changed_files",
        "verification_log",
        "summary",
    ]
    content_type: str
    path: str | None = None
    payload: dict[str, Any] | None = None
    created_at: str
```

#### `RunEvent`

```python
class RunEvent(BaseModel):
    run_id: str
    sequence: int
    event_type: str
    timestamp: str
    payload: dict[str, Any] = {}
```

### Event Taxonomy

Phase 0 should define a coding-runtime-specific event set rather than reusing generic `subagent_*` names as the durable contract.

Initial event types:

- `run_queued`
- `run_started`
- `context_assembled`
- `backend_started`
- `backend_finished`
- `verification_started`
- `verification_finished`
- `artifact_created`
- `run_completed`
- `run_blocked`
- `run_failed`
- `run_cancelled`

`sophia_prima` may continue to emit generic subagent events for UI compatibility, but those should be treated as presentation events rather than the runtime's canonical lifecycle contract.

### Verification Policy

Phase 0 should standardize how the supervisor asks for verification.

```python
class VerificationStep(BaseModel):
    name: str
    command: str
    required: bool = True


class VerificationPolicy(BaseModel):
    mode: Literal["none", "auto", "explicit"]
    steps: list[VerificationStep] = []
```

Rules:

- `none`: skip verification
- `auto`: runtime chooses a small set of checks when practical
- `explicit`: caller provides specific commands or recipes

### Artifact Rules

Artifacts should be written under one runtime-owned directory per run.

Recommended convention:

- `.sophia/forge/runs/{run_id}/task.json`
- `.sophia/forge/runs/{run_id}/prompt.json`
- `.sophia/forge/runs/{run_id}/backend_output.json`
- `.sophia/forge/runs/{run_id}/changed_files.json`
- `.sophia/forge/runs/{run_id}/verification/`
- `.sophia/forge/runs/{run_id}/summary.json`

### Phase 0 Code Moves

Add:

- `shared/sophia_forge_protocol/run_models.py`
- `shared/sophia_forge_protocol/event_models.py`
- `shared/sophia_forge_protocol/artifact_models.py`
- `shared/sophia_forge_protocol/verification_models.py`

Refactor:

- `agents/sophia_prima/src/sophia/coding_workers/base.py`
  - replace local dataclasses/schema helpers with shared protocol models
- `agents/sophia_prima/src/sophia/coding_workers/codex.py`
  - return shared `RunResult`-compatible output
- `agents/sophia_prima/src/sophia/coding_workers/claude_code.py`
  - same as above

Do not move yet:

- backend execution process launch code
- backend-specific command assembly
- supervisor routing logic in `sophia_prima`

### Phase 0 Acceptance Criteria

1. `sophia_prima` behavior is unchanged from the user's perspective.
2. Shared protocol models are used by both coding backends.
3. Output schemas are defined in the shared package.
4. Runtime artifacts use a stable naming convention.
5. Existing legacy `dev_worker` compatibility remains intact.

## Phase 1: `sophia_forge` Service

### Objective

Introduce an in-monorepo service boundary for coding execution.

`sophia_prima` should stop spawning backends directly and should instead call the runtime service.

### Proposed Package Layout

```text
services/
  sophia_forge/
    pyproject.toml
    README.md
    src/sophia_forge/
      api/
        main.py
        routes.py
      core/
        runtime.py
        scheduler.py
        workspace.py
        artifacts.py
        verification.py
      backends/
        base.py
        codex.py
        claude_code.py
      storage/
        run_store.py
      config.py

shared/
  sophia_forge_protocol/
    run_models.py
    event_models.py
    artifact_models.py
    verification_models.py

agents/
  sophia_prima/
    src/sophia/
      forge_client.py
```

### Why a Service in Phase 1

The service boundary gives:

- a reusable client contract
- clean observability around coding runs
- a path for non-`prima` callers
- separation between orchestration concerns and execution concerns

At the same time, keeping it in the monorepo avoids premature repo and release-management overhead.

## Phase 1 API

### `POST /v1/runs`

Creates a new coding run.

Request:

```json
{
  "client_name": "sophia_prima",
  "task": "Inspect the repository and add a missing market-data tool for event studies.",
  "workspace_root": "/workspace/sophia_engine",
  "readable_roots": ["/workspace/sophia_engine"],
  "writable_roots": ["/workspace/sophia_engine", "/workspace/sophia_engine/.sophia"],
  "backend": "codex",
  "timeout_sec": 900,
  "verification_policy": {
    "mode": "auto",
    "steps": []
  },
  "metadata": {
    "session_id": "telegram:acct1:peer42",
    "agent_id": "sophia_prima",
    "parent_run_id": "gw_run_123"
  }
}
```

Response:

```json
{
  "run_id": "forge_run_001",
  "status": "queued",
  "summary": "",
  "changed_files": [],
  "verification": [],
  "follow_ups": [],
  "artifact_ids": [],
  "error": null
}
```

### `GET /v1/runs/{run_id}`

Returns the latest result snapshot.

Response:

```json
{
  "run_id": "forge_run_001",
  "status": "completed",
  "summary": "Added the event-study market-data endpoint and registered the tool in pylon.",
  "changed_files": [
    "services/scrivener/src/api/market_data.py",
    "services/sophia_pylon/src/pylon/tools/market_data.py"
  ],
  "verification": [
    {
      "name": "targeted_pytest",
      "status": "passed",
      "command": "uv run pytest services/scrivener/tests/test_market_data.py",
      "required": true,
      "details": "1 passed"
    }
  ],
  "follow_ups": [],
  "artifact_ids": [
    "artifact_task",
    "artifact_backend_output",
    "artifact_verification"
  ],
  "error": null
}
```

### `GET /v1/runs/{run_id}/events`

Returns ordered runtime events.

Response:

```json
{
  "run_id": "forge_run_001",
  "events": [
    {
      "sequence": 1,
      "event_type": "run_started",
      "timestamp": "2026-03-16T18:05:00Z",
      "payload": {"backend": "codex"}
    },
    {
      "sequence": 2,
      "event_type": "context_assembled",
      "timestamp": "2026-03-16T18:05:01Z",
      "payload": {"workspace_root": "/workspace/sophia_engine"}
    }
  ]
}
```

### `GET /v1/runs/{run_id}/artifacts`

Returns the run's artifact index, not necessarily the full content of each artifact.

### `POST /v1/runs/{run_id}/cancel`

Best-effort cancellation.

Initial constraint:

- cancellation is only guaranteed before backend execution begins

## Runtime Execution Model

### `RuntimeScheduler`

Phase 1 only needs a local in-process scheduler.

Responsibilities:

- accept a `RunRequest`
- enqueue execution
- manage status transitions
- serialize run execution if needed initially

Non-responsibilities:

- distributed execution
- autoscaling
- durable queue semantics beyond the SQLite store

### `WorkspaceManager`

Responsibilities:

- validate readable/writable roots
- ensure output directories exist
- create per-run artifact directories

Phase 1 assumption:

- execution still happens against the configured workspace root
- no git worktree or container isolation yet

### `BackendAdapter`

Required interface:

```python
class BackendAdapter(ABC):
    name: str

    @abstractmethod
    async def run(self, request: RunRequest) -> RunResult: ...
```

Codex and Claude Code adapters in `services/sophia_forge/backends/` should be moved with minimal behavioral change from the current `sophia_prima` implementations.

### `VerificationRunner`

Responsibilities:

- choose commands when `mode=auto`
- execute explicit commands when `mode=explicit`
- capture stdout/stderr summaries
- mark required steps as passed or failed

Phase 1 recommended auto-heuristics:

- if a changed file is under `tests/`, do not infer anything extra
- if a changed file matches `*.py`, prefer a targeted `pytest` command when a nearby test file is obvious
- if no safe command is obvious, emit a `skipped` verification result with reason

## `sophia_prima` Integration Changes

### New Client Module

Add:

- `agents/sophia_prima/src/sophia/forge_client.py`

Responsibilities:

- submit `RunRequest`
- poll run status
- fetch artifacts or events when needed
- translate runtime result into existing supervisor/subagent result handling

### Supervisor Behavior

Keep the current supervisor decision logic in `subagents.py`.

Change only the execution mechanism:

- current: subagent delegates to local coding worker backend
- target: subagent delegates to `forge_client`, which submits to `sophia_forge`

### Event Compatibility

Retain existing `subagent_start`, `subagent_end`, and `subagent_error` events in `sophia_prima` for UI compatibility.

Additionally:

- persist `forge_run_id` in the event payload when available
- optionally mirror selected runtime events into the gateway run trace later

## Migration Plan

### Step 1

Create the shared protocol package and switch current coding workers to shared models.

### Step 2

Copy backend implementations into `services/sophia_forge/backends/` with minimal changes.

### Step 3

Implement `ForgeRunStore`, `WorkspaceManager`, `VerificationRunner`, and the API routes.

### Step 4

Add `forge_client.py` in `sophia_prima`.

### Step 5

Feature-flag the execution path:

- `CODING_RUNTIME_MODE=inline`
- `CODING_RUNTIME_MODE=forge_service`

Default for initial rollout:

- `inline`

### Step 6

Switch development and staging to `forge_service`, keeping `inline` as rollback.

## Testing Plan

### Unit Tests

- protocol model validation
- run status transition rules
- backend adapter output parsing
- verification result serialization
- storage read/write behavior

### Integration Tests

- `POST /v1/runs` creates a run and returns `queued`
- a backend run reaches `completed` with expected artifacts
- a failed backend run records `run_failed`
- `sophia_prima` in `forge_service` mode can delegate and consume results

### Compatibility Tests

- `inline` mode remains functional
- legacy `dev_worker` imports remain valid
- `sophia_prima` still emits expected high-level subagent events

## Acceptance Criteria

Phase 0 is complete when:

1. shared protocol models exist and are used by both existing backends
2. artifact paths are runtime-stable
3. `sophia_prima` behavior remains backward-compatible

Phase 1 is complete when:

1. `sophia_forge` exposes the run API described here
2. `sophia_prima` can delegate coding runs through `forge_client`
3. runtime events and artifacts are persisted in a forge-owned store
4. `inline` mode remains available as a rollback switch
5. at least one real coding workflow succeeds end-to-end through the service path

## Open Decisions

- whether `sophia_forge` should use FastAPI directly or a thinner internal server abstraction
- whether event streaming should be polling-only in Phase 1 or include SSE
- how aggressive `VerificationRunner` should be when inferring commands
- whether artifact payloads should be stored inline in SQLite or mostly as files on disk
- whether Phase 1 should allow one run at a time or modest bounded concurrency

## Recommendation

Build Phase 0 and Phase 1 exactly as an internal extraction, not a repo split.

If the service path proves stable, then Phase 2 can add stronger isolation and Phase 3 can add evaluation and benchmarking without reopening the core boundary decision.
